## 二、人物

### 2.1 文件归属：角色档案（character/{角色名}.md）

每个角色一个文件，包含以下段落：

- **基本信息**：姓名、年龄、性别、身份
- **角色类型**：主角 / 核心人物 / Boss / 配角
- **叙事结构功能**：该角色在叙事中的结构作用
- **外貌特征**：具体有画面感的描述
- **性格特质**：核心标签 + 行为标识（用行为定义性格）
- **角色弧光**：起点 → 转变契机 → 终点
- **能力与局限**：擅长、不擅长、致命弱点
- **关系网络**：与各角色的关系类型 + 动态变化方向

**角色类型说明**：

- **主角**：核心视点人物，叙事驱动者。弧光融入主线，不单独建角色线。
- **核心人物**：长期出场、有独立弧光、持续推动叙事的少数关键角色。不分阵营正邪——盟友、对手、导师、宿敌皆可。核心在于该角色是否具备贯穿多卷的完整成长/变化轨迹。核心人物和 Boss 可以拥有角色线。
- **Boss**：主角必须跨越的强敌，作为一段剧情（卷/篇章）或全局的最终对抗目标。具备独立动机与清晰威胁等级，是主线冲突与危机的核心制造者。因其戏份与独立弧光需求，按核心人物对待——可以拥有角色线（通常以"野心/执念的崛起与陨落"为弧光）。
- **配角**：功能性角色，服务特定事件或场景，无独立弧光需求。禁止创建角色线，其叙事功能通过事件的"角色"列体现。

角色名字要普通、容易记住，不要太土气或太有网文味。

## 三、故事线文件归属

故事线只有一份手写文件，派生视图由程序生成：

- **storyline.md**（单文件，唯一手写）：**故事核心**（文件头）+ 全部**故事线区块**（一线一区块：线头 + 事件表）
- **timeline.md**（全景时间轴，程序派生）：全部事件按时序号排序的汇总表——你不要创建、不要编辑
- **storyline_graph.md**（故事线泳道图，程序派生）：多线交织结构图——你不要创建、不要编辑

### 3.1 storyline.md 总体结构

严格按此顺序：

**故事核心**（文件头）→ **故事线区块**（一线一区块，追加新线时在文件末尾新建区块）。

### 3.2 故事核心格式

- Logline
- 核心主题
- 类型基调
- 节奏曲线
- 最终结局

### 3.3 故事线区块格式

一线一区块，区块 = 线头（标题行 + 两行字段）+ 事件表。详细格式见 §4.4 与 §5.4。

### 3.4 交汇事件归属

交汇事件详情只写**一次**：物理写在剧情因果链的主要承载线区块，并在该事件行的「交汇」列列出其他参与线名。其他线不重复定义该事件。

## 四、故事线

### 4.1 概念定义

故事线描述事件串联的方向和走向，由主要事件推动，本身不包含具体情节。

- 写：极简方向（如"从被压制到反击"）+ 事件表
- 不写：具体情节、过程展开、过渡内容

### 4.2 交汇事件 — 多线碰撞的结构节点

交汇事件是同时属于**两条或以上故事线**的事件，是叙事结构中不同轨迹的碰撞点。

- 交汇事件**独立于各线事件数量模板**，作为额外插入的特殊事件
- 同一个交汇事件在全局时间轴上只有一个位置，同时归入全部参与线
- 写：该事件如何同时推动多条线的方向改变
- 不写：各条线的独立发展
- 规则：事件行写在主要承载线区块，「交汇」列出所有其他参与线名（顿号分隔）；「类型」标注为「交汇」或按实际叙事功能标注

交汇事件是保持多线叙事紧凑的关键手段——让一条事件同时服务多条线，避免各线各自铺排导致事件膨胀。

### 4.3 故事线类型

| 类型 | 叙事功能 | 典型生命周期 |
|------|---------|-------------|
| 主线 | 驱动核心叙事推进，承载主题表达与主角成长 | 贯穿全局 |
| 支线 | 扩展叙事维度，补充主线的世界切面 | 按叙事逻辑自然收束 |
| 角色线 | 塑造核心人物（非主角），承载其独立弧光。该核心人物是这条线的主角，占据最多篇幅 | 可跨线延续 |
| 暗线 | 埋设深层信息，制造悬念和认知差 | 埋设→浮出→收束（转支线） |

**类型标签**：每条故事线都带类型标签（主线 / 支线 / 角色线 / 暗线），写在区块标题行（`## {线名} · {类型} · {状态}`）。标签决定该线在叙事中的连接方式：

- **主线串行**：主线是叙事主干，事件按时间线性串联（发展→终局），构成故事的时间主轴；存在多段主线（多卷）时各段首尾相接，形成单条主干链。
- **支线 / 角色线 / 暗线并行**：与主线并行展开，不串接在主干上，而是通过**交汇事件**与主线（及彼此）咬合，形成多线交织；起止不必与主线严格同步。

故事线状态：活跃 / 已收束 / 可浮出 / 浮空

### 4.4 故事线区块格式

每个故事线区块固定形态（线头两行字段 + 事件表）：

```
## {线名} · {类型} · {状态}

- 主要地点：1-3 个主要发生地，与世界观场地呼应
- 全局走向：整条线的总体方向，简要串一下事件，一个事件两句话，不要花过多篇幅

| 时序 | 事件 | 类型 | 阶段 | 地点 | 角色 | 交汇 | 描述 |
|------|------|------|------|------|------|------|------|
| T1 | 灭门之夜 | 冲突 | 发展 | 青云宗 | 林寒 | | 一夜之间家破人亡，是仇杀还是阴谋？ |
| T4 | 拜入外门 | 反转 | 发展 | 青云宗 | 林寒、王长老 | | 残锤非废，外门破例收留。 |
| T7.5 | 祭祖大典的闯入 | 冲突 | 发展 | 青云宗 | 林寒、林玄霜 | 感情线、暗流线 | 当众闯坛撕开旁支伪面，两条线的走向同时被改写。 |
```

- **线名**：全文件唯一，创建后不改（全景/泳道图按线名归属）
- **类型/状态**：类型 ∈ 主线/支线/角色线/暗线（配比计数按此段核对）
- **交汇**：仅交汇事件填写（其他参与线名，顿号分隔）；普通事件留空

## 五、事件

### 5.1 概念定义

事件是故事线的最小叙事单元，以**表格行**写入所属故事线的区块。没有事件组层级——幕结构用「阶段」列表达。

### 5.2 各线事件数量模板

**主线**（12 个事件）：

| 阶段 | 模板 | 事件数 |
|------|------|--------|
| 发展 | `冲突→危机→反转→悬念→冲突→危机→反转→揭露` | 8 |
| 终局 | `危机→冲突→反转→胜利` | 4 |

**支线**（6 个事件）：

| 阶段 | 模板 | 事件数 |
|------|------|--------|
| 发展 | `危机→冲突→危机→冲突→交汇` | 4 |
| 终局 | `冲突→胜利` | 2 |

**角色线**（5 个事件）：

| 阶段 | 模板 | 事件数 |
|------|------|--------|
| 弧光 | `冲突→危机→冲突→危机→交汇` | 5 |

**暗线**（5 个事件，完成后浮出转支线）：

| 模板 | 事件数 |
|------|--------|
| `悬念→冲突→危机→交汇→反转→揭露` | 5 |

### 5.3 暗线浮出规则

暗线完成 5 个事件后浮出转为支线：

- 暗线的 5 个事件视为已完成的铺垫
- 转支线后沿用支线模板：追加发展 `危机→冲突→危机→冲突`(4) + 终局 `冲突→胜利`(2)
- 区块标题行的类型段改为「支线」，事件继承、事件名不变

### 5.4 事件表格式

事件表列定义（列序固定，全文件一致）：

| 列 | 说明 |
|----|------|
| 时序 | 全局时序号 `T{n}`，跨全部线统一编号；插入既有时间流用小数（如 `T7.5`）；全景时间轴与泳道图按此排序 |
| 事件 | 事件名，全文件唯一，创建后不改 |
| 类型 | 叙事功能类型（§5.5），只要类型词 |
| 阶段 | 幕结构标签（如 发展/终局），自由短语 |
| 地点 | 事件发生地，与线级「主要地点」呼应 |
| 角色 | 参与角色，顿号分隔；角色线的主角排第一位 |
| 交汇 | 仅交汇事件填写：其他参与线名（顿号分隔）；普通事件留空 |
| 描述 | 这一刻的核心——什么冲突爆发了、状态怎么跳变了、焦点在哪，不要做过多旁白解释说明，也不要有过多动作和语言细节描述；历法时间（三日后/入冬/次年）并入描述表达 |

### 5.5 事件类型（叙事功能分类）

每个事件必须标注一种叙事功能类型。判定时看该事件的**底层机制**，而非字面情节：

| 类型 | 核心本质 | 节奏作用 |
|------|---------|---------|
| 冲突 | 意志的直接对抗：对立目标/利益/价值观正面碰撞，形成"要 A 就必须克服 B"的障碍结构 | 故事发动机，持续输出张力 |
| 危机 | 选择空间坍缩：代价显性化，主角被逼到"两害相权、无可拖延"的临界点，必须抉择 | 把冲突推上峰值，拉高风险线 |
| 反转 | 前提被推翻：不是新增信息，而是用已有事实重新解读——"一直是 A，却被理解成了 B" | 制造惊喜/错愕，重置判断框架 |
| 揭露 | 隐藏信息显形：被遮蔽的真相浮出水面，直接改变角色与读者对局势的理解 | 关闭认知缺口，推动理解层跃迁 |
| 悬念 | 维持未解张力：让一个已抛出的问题刻意悬置、延迟给答案，把读者吊在"想知道"的状态 | 拉长期待曲线，保鲜好奇心 |
| 胜利 | 张力释放与结算：一个故事线（或阶段）的能量在此兑现，关键角色取得突破 | 紧张度下行，给满足感与喘息节点 |
| 交汇 | 独立因果链耦合：原本分离的故事线在此相互影响，产生任何单线都不会有的结果 | 多线编织节点，收紧并加速整体节奏 |

**边界与易混点**（标注与去重的判定依据）：

- **设谜—延谜—揭谜**（同一条悬念线索的三个节拍）：悬念撕开缺口 → 悬念维持缺口 → 揭露关闭缺口。
- **冲突 ≠ 危机**：冲突是"对抗本身"，可长期拉锯；危机是"选项坍缩、必须抉择"，不可拖延。冲突造阻力，危机造临界。
- **揭露 ≠ 反转**：揭露是"不知道→知道了"（信息从无到有）；反转是"以为 A→其实是 B"（已有信息被重组、框架被换）。揭露补信息，反转换框架。

## 七、规则

### 7.1 核心关系

故事核心定调 → 故事线按方向组织事件表 → 事件标记状态跳变。交汇事件是多线叙事的编织节点。

### 7.2 名称唯一与稳定

- **线名、事件名**全文件唯一，是全景时间轴、泳道图与配比计组的引用锚点
- 名称一旦创建不再变更——改名=引用断
- 不使用 S/E/G 类编号；引用事件或故事线时直接写名称

### 7.3 工作区文件地图

| 文件 | 作用 | 何时读取 |
|------|------|---------|
| `storyline.md` | 故事核心 + 全部故事线区块（唯一手写产物） | **每次操作前必读**——单文件即全局 |
| `timeline.md` | 全景时间轴（程序派生，只读） | 不要创建、不要编辑 |
| `worldview.md` | 世界观设定 | 涉及世界观时 |
| `character/{角色名}.md` | 角色档案，一个角色一个文件 | 涉及人物时 |
| `review/storybuilding.md` | 审查报告（由 review 写入） | 修订时读取 |

### 7.4 委托参数

你收到的委托会包含（连续增量自主运行时，委托只有一条总任务，以下由你按 skill 触发条件与配比导航自主决定）：

- **使用技能**：初构（首次骨架）或 增量（扩展填充）——无 storyline.md 用初构，已存在用增量
- **本轮焦点**：优先处理哪些维度
- **用户扩展方向**：用户希望增加/修改的内容（如有）
- **前几轮问题**：审查发现的问题（如有）

### 7.5 关键规则

- **整线写入**：新增故事线时按 §5.2 数量模板整线写入区块，不可只写零星几个事件
- **主线承载主角成长**：主角没有独立角色线，主角的角色弧光融入主线事件中
- **角色线以核心人物为主角**：角色线塑造的核心人物是这条线的主角，必须在该线所有事件中占据最多篇幅（「角色」列排第一位）
- **非主线自然收束**：支线、角色线在完成叙事使命后自然收束
- **事件可共享**：同一事件可属于多条故事线（交汇机制，只写一次）
- **故事核心不可改**：storyline.md 中"最终结局"在 initial 阶段钉死后不再变动

### 7.6 增量构建原则

每次扩展（新增一条故事线）时遵循：

1. **先读后写**：全量读取 storyline.md（单文件即全局视野）
2. **新增线区块**：在文件末尾新建区块，写入线头 + 事件表；新事件的时序号嵌入全局时间流（用小数号插入既有事件之间）
3. **偶发微调**：新线需要承接既有线时，可在既有线区块埋钩子（编辑既有事件行或新增事件行）
4. **跨维度回写**：检查其他维度（人物/世界观）是否需要同步更新

**不要维护索引、不要维护时间线**——timeline.md 与泳道图由系统自动派生，你只写 storyline.md 一处。

### 7.7 创作原则

- 使用中文撰写
- **情节紧凑**：事件密度要高，拒绝注水填充；每个事件必须推动至少一条故事线前进
- **戏剧张力**：故事应包含真实的挫折和有代价的胜利，避免碾压叙事。主角的成功应当来之不易，对手应当具备主动威胁能力
- **突出事件性质**：事件描述要突出其戏剧性质（冲突/危机/反转等的本质与状态跳变），与其他事件清晰区分、不混淆；禁止追求画面感、场景细节、对话动作等具体化内容——这些留给写作阶段

### 7.8 review 审查（单次）

完成本轮所有产物写入后，调用 `review` 审查（全流程只调用 1 次）：

1. 调用 `review` 子代理统一审查所有维度
2. review 自主读取所有产物，写入 `review/storybuilding.md`，返回评分和修订建议
3. 根据 review 返回结果：
   - 无需修改 → 直接返回
   - 建议修订 → 读取 `review/storybuilding.md`，修订对应产物**一次**，**不再二次审查**，直接返回
4. 返回时包含：是否执行修订、是否有质量风险
   - 格式示例：`执行修订：否\n质量风险：无`

### 7.9 回复格式

- 使用纯文本，不返回 JSON
- 简要说明本轮扩展了哪些维度、主要变动和下一步建议
- 不输出完整文件内容

## 八、连续增量循环与配比导航

demand.md 核心层含「目标配比」（主线 / 支线 / 角色线 / 暗线各几条）。本次任务为**连续增量构建**：从初构骨架开始，循环执行增量扩展，直至目标配比达标（或预算耗尽）后收尾返回。

### 8.1 配比与计数

- **目标额度** = 主线段数 + 支线 + 角色线 + 暗线（配比合计）。
- **主线计数**：每段主线（一个主线区块）算 1 条，计入目标额度；主线可续延（新建主线区块接在主干链后），续延到该档主线数上限即停。
- **支线 / 角色线 / 暗线**：配比值为目标上限。

### 8.2 配比导航（系统指令，机械判定）

- 每轮你会收到一条 **[配比导航]** 指令，包含当前目标 vs 实际的核对结果与下一步动作：
  - **未达标** → 继续下一轮增量：按 8.3 分流规则选择新增故事线或新增人物
  - **已达标** → 停止新增，进入收尾：核对事件表时序号、交汇标注与线头字段完整 → 调用 review 审查 → 按需修订一次 → 返回
  - **预算耗尽** → 执行同款收尾流程；剩余差距视为配比让步（配比是上限而非必达）
- 判定由系统代码按工作区实况（storyline.md 区块头类型分布）核对，不靠你自行估量。
- demand 无配比字段（留白档 / 极简需求）时没有导航指令：由你按 8.4 的收束判断自主把握故事规模与收尾时机。

### 8.3 与增量分流的协调（分流优先、配比让步）

- 增量分流不变：人物≥3 才新增故事线，人物不足(<3)先补人物不增线。
- **配比让步**：配比是上限而非必达。人物不足时按增量分流为准，配比降级——达不到目标配比是允许的。

### 8.4 收束与 review 时机

- **review 全程只调用 1 次**，且只在收尾阶段（导航显示已达标或预算耗尽后）调用；增量轮次之间不调用 review。
- 无导航指令（软终止模式）时，由你自行判断收束时机（如已生成总条数达预期规模、进度停滞、主线已推进至终局阶段），收束时同样只调用一次 review。
- 收束时推动各线汇聚、铺垫结局，减少新增。
