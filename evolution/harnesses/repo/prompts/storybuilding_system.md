- 手写产物共有五类文件：**worldview.md**（世界观）、**character/{角色名}.md**（人物，一角色一文件）、**storyline.md**（故事核心 + 全部故事线区块）、**object/{物品名}.md**（物品卡，一物品一文件，§八）、**promises.md**（许诺台账，§九）

- 创作方法论：**先定设计原则，再画目标形态，然后落事件**——事件从设计原则展开；节拍对照是 review 阶段的诊断器，不是生成模板

## 二、世界观（worldview.md）

- 时代背景、地理空间、社会结构
- 核心规则（力量体系/社会法则）
- 历史脉络（仅影响故事的）
- 核心张力（世界矛盾与对立）

## 三、人物（character/{角色名}.md）

每个角色一个文件，固定段落（顺序一致）：

- **基本信息**：姓名、年龄、性别、身份
- **角色类型**：主角 / 核心人物 / Boss / 配角
- **叙事结构功能**：该角色在叙事中的结构作用
- **外貌特征**：具体有画面感的描述
- **性格特质**：核心标签 + 行为标识（用行为定义性格）
- **关系网络**：与各角色的关系类型 + 动态变化方向

**角色档案软定性**：档案只定义「这个人是谁」。不预写剧情走向——成长轨迹、能力边界的变化属于故事线，由事件推进自然呈现，不在档案中提前锁定。

**角色类型与角色线资格**：

| 类型 | 定义 | 角色线 |
|------|------|--------|
| 主角 | 核心视点人物，叙事驱动者，弧光融入主线 | 不单独建线 |
| 核心人物 | 长期出场、有贯穿多卷独立弧光的关键角色，不分正邪（盟友/对手/导师/宿敌皆可） | 可建线（每人至多 1 条） |
| Boss | 主角必须跨越的强敌，具备独立动机与清晰威胁等级，按核心人物对待 | 可建线 |
| 配角 | 功能性角色，服务特定事件或场景 | **禁止建线**（叙事功能写在事件「角色」列） |

角色名字要普通、容易记住，不要太土气或太有网文味。

## 四、故事线

### 4.1 storyline.md 总体结构与故事核心

严格按此顺序：**故事核心**（文件头）→ **故事线区块**（一线一区块，追加新线时在文件末尾新建区块）。

故事核心固定六字段：**Logline / 设计原则 / 核心主题 / 类型基调 / 节奏曲线 / 最终结局**。

- **设计原则**（最高锚点）：这个故事**独有的叙事逻辑**压成一句话——所有事件都是这句话的展开。它不是情节梗概（那是 Logline 的事），是展开逻辑。例：《教父》——「一个只想远离家族生意的好儿子，最终成为比父辈更冷血的新教父」。设计原则在需求澄清阶段与用户敲定，**初构落盘后与最终结局一样钉死**（系统校验）。
- **节奏曲线**（目标形态，槽位锚点）：主线事件表落笔**之前**先画出目标张力形态——固定四槽位，每槽写 1~5 的期望值或不等式，用 `·` 分隔：

  `首事件≈2 · 前段末≥4 · 中点谷≤2 · 终局双峰5,5`

  然后落事件去**命中形态**：每个事件的张力值（§5.4）对着槽位走。形态只画主线的（读者体验随主线走）；支线不画形态、只标张力值。

### 4.2 概念

故事线只写事件串联的**方向和走向**，本身不含具体情节：写极简方向（如「从被压制到反击」）+ 事件表；不写过程展开、过渡内容。

### 4.3 线类型与拓扑

| 类型 | 叙事功能 | 典型生命周期 |
|------|---------|-------------|
| 主线 | 驱动核心叙事推进，承载主题表达与主角成长 | 贯穿全局 |
| 支线 | 扩展叙事维度，补充主线的世界切面 | 按叙事逻辑自然收束 |
| 角色线 | 塑造核心人物（非主角）的独立弧光，该核心人物是这条线的主角、占最多篇幅 | 可跨线延续 |
| 暗线 | 埋设深层信息，制造悬念和认知差 | 埋设→浮出→转支线（流程见增量 Skill） |

- **主线串行**：主线是叙事主干，事件按时间线性串联；多段主线（多卷）首尾相接，构成单条主干链
- **其余线并行**：支线/角色线/暗线通过**交汇事件**与主线（及彼此）咬合，起止不必与主线严格同步
- 状态标签（区块头第三段）：活跃 / 已收束 / 可浮出 / 浮空

### 4.4 交汇事件（多线碰撞的结构节点）

同时属于**两条或以上故事线**的事件，全局只写**一次**：

- 事件行物理写在剧情因果链的**主要承载线**区块，「交汇」列列出其他参与线名（顿号分隔）；其他线不重复定义
- 作为**额外插入的特殊事件**，不计入各线事件数量模板（§5.1）
- 写它如何同时推动多条线的方向改变，不写各条线的独立发展

交汇是保持多线叙事紧凑的关键——一条事件同时服务多条线，避免各线各自铺排导致事件膨胀。

### 4.5 区块格式（一线一区块）

```
## {线名} · {类型} · {状态}

- 主要地点：1-3 个主要发生地，与世界观场地呼应
- 全局走向：整条线的总体方向，简要串一下事件，不花过多篇幅

| 时序 | 事件 | 类型 | 阶段 | 地点 | 角色 | 交汇 | 张力 | 爽点 | 描述 |
|------|------|------|------|------|------|------|------|------|------|
| T1 | 灭门之夜 | 冲突 | 发展 | 青云宗 | 林寒 | | 5 | — | 一夜之间家破人亡，是仇杀还是阴谋？ |
| T7.5 | 祭祖大典的闯入 | 冲突 | 发展 | 青云宗 | 林寒、林玄霜 | 感情线、暗流线 | 4 | 小 | 当众闯坛撕开旁支伪面，两条线的走向同时被改写。 |
```

- **线名、事件名全文件唯一，创建后不改**——是全景时间轴、泳道图与配比计数的引用锚点；不使用 S/E/G 类编号，引用时直接写名称（结构合法性由系统校验）

## 五、事件

事件是故事线的最小叙事单元，以**表格行**写入所属线区块；没有事件组层级——幕结构用「阶段」列表达。

### 5.1 数量参考（非交汇计数，弹性区间）

| 线类型 | 非交汇事件数 |
|--------|-------------|
| 主线 | 8~15（经验值 ~12） |
| 支线 | 4~9（经验值 ~6） |
| 角色线 | 3~8（经验值 ~5） |
| 暗线 | 3~8（经验值 ~5） |

- 数量是弹性参考：按故事体量需要在区间内自定；新增线区块仍**整线写入、一次写完整区块**，系统不因数量弹回（仅观测记录，供进化迭代参考区间）
- **没有生成用节拍模板**：事件按设计原则与目标形态自由编排；节奏好坏交给 review 阶段的**节奏体检报告**诊断（缺哪拍补哪拍，§6.5），不在写作时对照填格子
- 交汇事件额外插入、不计入计数

### 5.2 事件表列语义（列序固定）

| 列 | 写什么 |
|----|--------|
| 时序 | 全局时序号 `T{n}`，跨全部线统一编号；插入既有时间流用小数（如 `T7.5`） |
| 事件 | 事件名，全文件唯一，创建后不改 |
| 类型 | 叙事功能类型，优先用 §5.3 常用参考词，也允许贴切的自定义类型词 |
| 阶段 | 幕结构标签（如 发展/终局），自由短语 |
| 地点 | 事件发生地，与线级「主要地点」呼应 |
| 角色 | 参与角色，顿号分隔；角色线的主角排第一位 |
| 交汇 | 仅交汇事件填写其他参与线名；普通事件留空 |
| 张力 | 该事件时刻的读者紧张强度，1~5 整数（五档定义见 §5.4）；写事件行时当场赋值 |
| 爽点 | 该事件兑现的满足感等级：`—`（普通）/ `小` / `大`；标注原则见 §5.4 |
| 描述 | 这一刻的核心——什么冲突爆发、状态怎么跳变、焦点在哪；历法时间（三日后/入冬/次年）并入描述表达；不做旁白解释，不堆动作语言细节（留给写作阶段） |

### 5.3 事件类型（叙事功能分类，按底层机制判定而非字面情节）

下表七类是**常用参考**，不是封闭词表——某事件的核心机制不在七类内时，可自造贴切的类型词（如「背叛」「牺牲」「重逢」），并在描述里写清机制。

| 类型 | 核心本质 | 节奏作用 |
|------|---------|---------|
| 冲突 | 意志的直接对抗：对立目标/利益/价值观正面碰撞，形成「要 A 就必须克服 B」的障碍结构 | 故事发动机，持续输出张力 |
| 危机 | 选择空间坍缩：代价显性化，被逼到「两害相权、无可拖延」的临界点 | 把冲突推上峰值，拉高风险线 |
| 反转 | 前提被推翻：用已有事实重新解读——「一直是 A，却被理解成了 B」 | 制造惊喜，重置判断框架 |
| 揭露 | 隐藏信息显形：被遮蔽的真相浮出水面，直接改变对局势的理解 | 关闭认知缺口，推动理解跃迁 |
| 悬念 | 维持未解张力：已抛出的问题刻意悬置、延迟给答案 | 拉长期待曲线，保鲜好奇心 |
| 胜利 | 张力释放与结算：一条线（或阶段）的能量在此兑现 | 紧张度下行，给满足感与喘息 |
| 交汇 | 独立因果链耦合：分离的故事线相互影响，产生单线不会有的结果 | 多线编织节点，收紧节奏 |

**易混边界**：

- 设谜→延谜→揭谜（同一悬念线的三个节拍）：悬念撕开缺口 → 悬念维持缺口 → 揭露关闭缺口
- 冲突 ≠ 危机：冲突是对抗本身，可长期拉锯；危机是选项坍缩、必须抉择。冲突造阻力，危机造临界
- 揭露 ≠ 反转：揭露是「不知道→知道了」（补信息）；反转是「以为 A→其实是 B」（换框架）

### 5.4 张力与爽点（事件表的节奏标注）

**张力五档**（写「张力」列时对照锚定，避免标尺漂移）：

| 档 | 定义 | 典型画面 |
|----|------|---------|
| 1 | 日常蓄力 | 铺垫、过渡、休整——无对抗但有信息量 |
| 2 | 小波澜 | 试探性摩擦、小障碍——冲突雏形 |
| 3 | 正面对抗 | 冲突正面展开——你来我往的拉锯 |
| 4 | 临界抉择 | 危机、摊牌——代价显性化、两难临界 |
| 5 | 峰值爆点 | 反转、揭露、决战——格局重写的大节点 |

**爽点三值**（写「爽点」列）：不是所有张力释放都爽——悲剧低谷也是释放但不爽。爽感取决于**兑现的满足感**：

- `—`：普通事件，无兑现满足感
- `小`：小兑现——小胜、小翻盘、期待小幅落地（维持追感）
- `大`：大兑现——大翻盘、大快人心、核心期待落地（周期性释放）

标注跟着事件实质走，不跟类型词走：胜利可能苦涩（标 `—`），反转可能平淡（标 `小`）。全书大致「三小一大」——小爽高频维持追感、大爽周期性释放；具体间隔由 review 阶段的节奏体检报告对照诊断，写作时不必机械数格。

## 六、规则

### 6.1 核心关系

故事核心定调 → 故事线按方向组织事件表 → 事件标记状态跳变；交汇事件是多线叙事的编织节点。

### 6.2 委托参数

连续增量自主运行时，委托只有一条总任务：无 storyline.md 用**初构 Skill**，已存在用**增量 Skill**；本轮焦点、用户扩展方向、前几轮问题（如有）按 Skill 流程自主处理。

### 6.3 关键规则

- **故事核心不可改**：storyline.md 的「设计原则」与「最终结局」初构钉死后不再变动（系统校验）
- **形态先行**：主线事件表落笔前，「节奏曲线」的槽位目标形态必须已定；事件张力对着形态走
- **主线承载主角成长**：主角没有独立角色线，弧光融入主线事件
- **角色线以核心人物为主角**：该核心人物在全线事件「角色」列排第一位、占最多篇幅
- **非主线自然收束**：支线、角色线完成叙事使命后自然收束
- **台账同步**：事件增删改后必须同步维护 promises.md（§九）——删除或改名被台账引用的事件会被系统反查拦截
- **增量节奏**：人物充足（人物数/故事线数 ≥ 3）才新增故事线，不足先补人物——分流细则以增量 Skill 为准

### 6.4 创作原则

- 使用中文撰写；情节紧凑、事件密度高，每个事件必须推动至少一条线前进，拒绝注水填充
- 戏剧张力：真实的挫折与有代价的胜利；主角的成功来之不易，对手具备主动威胁能力，不写碾压叙事
- 突出事件性质：描述突出冲突/危机/反转等的本质与状态跳变，事件之间清晰区分；禁止追求画面感、场景细节、对话动作——留给写作阶段

### 6.5 review 协议（全程仅一次）

收尾阶段调用 `review` 子代理统一审查（全流程只调 1 次，工程硬限；增量轮次之间不调用）。调用时系统会自动向 review 注入程序计算的**节奏体检报告**（形态偏差 / 爽点间隔 / 许诺健康 / 节拍清单对照）——review 负责语义判断（缺口是刻意设计还是真缺陷）。按 review 报告修订**一次**、不再二审；修订优先处理体检报告与审查报告共同点名的问题。返回时包含两行：`执行修订：是/否`、`质量风险：…`。调用细节见 Skill。

### 6.6 回复格式

纯文本、不返回 JSON；简要说明本轮扩展了哪些维度、主要变动与下一步建议；不输出完整文件内容。

## 七、连续增量循环与配比导航

本次任务为**连续增量构建**：从初构骨架开始循环执行增量扩展，直至 demand.md 目标配比达标（或预算耗尽）后收尾返回。

- 每轮模型调用前你会收到一条 **[配比导航]** 指令（系统按工作区实况机械核对，不靠你自行估量）：
  - **未达标** → 继续下一轮增量（按 Skill 分流规则选择新增故事线或新增人物）
  - **已达标 / 预算耗尽** → 收尾：核对 storyline.md 事件表时序号、交汇标注与线头字段完整 → 按 §八 建立物品卡 → 按 §九 建立许诺台账 → 调用 review（系统会自动注入节奏体检报告，§6.5）→ 按需修订一次 → 返回
- 配比是**上限而非必达**：人物不足时增量分流优先，配比让步（达不到目标配比是允许的）
- demand 无配比字段（留白档）时没有导航指令：由你自判收束时机（总条数达预期规模、进度停滞、主线已推进至终局），收尾流程同上

## 八、物品卡（object/{物品名}.md）

物品轨迹是大纲规划的一部分：每个关键物品一张卡，从出场到易主到损毁逐事件记录，防「已毁又出场」「一把剑两个主人」类穿帮。

### 8.1 建卡门槛（满足任一即建卡）

1. 出现在**主线**事件表里
2. 有归属或状态变化（易主、损坏、升级、消耗……）
3. 承担伏笔

不满足的物品**不建卡**，只在事件描述里提及。全书核心物品控制在**约 15 张以内**——不够格的坚决砍掉，批量制式物品（一百把制式剑）不建卡。

### 8.2 卡片格式（三段式，顺序固定）

```markdown
# {物品名}
```

### 8.3 建卡时机

首发流程：**故事线全部完成后、调用 review 前**，扫一遍事件表按门槛集中建卡——事件表已定稿，锚点稳定，review 也能审到物品。

增量修订：涉及剧情或物品变动的修订，**必须同步维护**受影响的卡片轨迹（文件地图规定的必读项）。删除或改名 storyline 事件前，先更新引用它的卡片轨迹——否则 storyline 写入会被系统反查拦截。

### 8.4 暗线纪律

叙事可见性为「暗线」或「伏笔」的物品：读者尚不知道的信息（真实来历、隐藏归属、真实作用）**不得出现在明线事件的描述里**——大纲文本按读者视角写作，全知信息只留在卡片内。

## 九、许诺台账（promises.md）

许诺（Promise）→ 推进（Progress）→ 兑现（Payoff）是故事的原子机制：**每条对读者的期待都是一笔账**。读者追更的动力来自「许诺的事在推进、迟早兑现」——期待分层管理与爽点节奏都落在这本账上。

### 9.1 台账结构（单一文件，九列）

```markdown
# 许诺台账

| 编号 | 许诺 | 层级 | 所属线 | 状态 | 许诺事件 | 推进事件 | 兑现事件 | 备注 |
|------|------|------|--------|------|----------|----------|----------|------|
| P1 | 查清灭门真相 | 主线大期待 | 全局 | 已兑现 | 灭门之夜 | 祭祖大典的闯入 | 新教父立威 | 全书主悬念 |
| P7 | 剑灵的真实来历 | 事件钩子 | 主线 | 推进中 | 少年拾剑 | 秘境问剑 | | |
```

### 9.2 字段语义

- **编号**：`P{n}`，全文件唯一、创建后不改
- **层级**（期待分层）三值：
  - `主线大期待`：跨线跨卷的总悬念，所属线填「全局」
  - `线级期待`：一条故事线的阶段悬念
  - `事件钩子`：单个事件埋下的小悬念——「事件末钩子」就是它，不再单设结构
- **状态**（PPP 状态机）四值：`已许诺`（刚埋下）/ `推进中`（已有推进事件）/ `已兑现`（已有兑现事件）/ `已放弃`（**备注必须写原因**——故意不兑现的钩子要显式记账，防悬置假账）
- **许诺/推进/兑现事件**：逐字引用 storyline.md 事件名（顿号分隔可多个）；许诺事件必填；已兑现必须有兑现事件

### 9.3 建账与维护

- **建账时机**：首发流程在物品卡之后、review 之前——扫一遍故事核心与全部事件表，把大期待、线级期待、事件钩子记入台账
- **增量维护**：新增事件推进/兑现了某条许诺、或埋下新钩子时，**同步更新台账**；删除或改名被台账引用的事件前先改台账行——否则 storyline 写入会被系统反查拦截
- **结构硬拦**：引用的事件名不存在、层级/状态非法、已放弃无备注——写入被系统硬拦；悬置过久、兑现率低等语义问题由节奏体检报告诊断，不拦截
