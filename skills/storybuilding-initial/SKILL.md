# storybuilding-initial

首次故事骨架构建流程。**内容规范唯一真相源是技能 storybuilding-specs**（质量总则/世界观/人物档案/故事线/事件/文风/物品卡全部在其中，系统提示词只管流程）——步骤 3 动笔前读取（本会话首次读取后不必重读），跳读等于无规范写作。两个硬性约束：
1. **只生成主线（1 条）**。支线 / 暗线 / 角色线一律交给增量 Skill 后续添加，初构阶段不生成。
2. **storyline.md "故事核心"段落的"最终结局"初构定为草稿基线**：回执轮确认为初版草稿，后续轮次可随叙事需要修订。

## 工作流程

### 步骤 0 — 首轮运行判定（方向提案）

若本轮为首次运行（storyline.md 尚不存在，系统注入 [交互模式·提案轮] 指令）：

**本轮不写任何产物**（写入会被提案闸门硬拦截，见拦截提示），按系统提示词「方向提案协议」执行：

1. 读取 demand.md，消化需求后设计 **2-3 套真实不同的方向方案**（每套五件套：方向名 / 一句话定位 / 核心画面 / 关键锚点 / 与其他方案的差异；关键参数由你定好打包，不让用户逐题做抽象决策）
2. **调用 `confirm_with_user` 工具**提交提案全文（question=2-3 套方案全文，options=快捷路径如「选定方案 1」「选定方案 2」「选定方案 3」「我要调整，见补充」）
3. 用户回复 = 拍板结果，**一次有效回复即动笔（一段式，不做二次确认）**：选定 → 以选定稿为锚进入步骤 1；调整/自提 → 消化吸收后直接进入步骤 1；明示「不用问了直接写」→ 以你的推荐方案直接动笔

**写入闸门在工具一次有效回复后即释放**。
**禁止用纯文本回复代替工具调用**——产物未写出时终局会被产物校验拦回，运行无法结束。
未注入提案轮指令（如评估集预置流 receipt_skip）时跳过本步，直接进入步骤 1

### 步骤 1 — 读取需求背景

读取 `demand.md`，了解用户需求和创作背景。
- demand.md 由主代理维护，你只能读取，不能写入、编辑或删除。

### 步骤 2 — 读取已有产物

读取工作区中已有的文件（首次构建时可能不存在，属于正常情况）。

### 步骤 3 — 产出骨架

先完整读取技能 **storybuilding-specs**（内容规范唯一真相源），再按其规范产出骨架。

写入顺序：
1. `worldview.md`（世界观是底层基础）
2. `character/*.md`（人物在世界观中活动）
3. `storyline.md`（故事核心 + 主线 1 个区块，内含完整事件表）

**storyline.md 是唯一手写的故事线产物**——不要创建 storyline/ 目录，不要创建 timeline.md（全景时间轴由系统自动派生）。

**最小骨架必须包含：**
- storyline.md 中的"故事核心"（Logline、核心主题、类型基调、节奏曲线、最终结局）
- storyline.md 中的主线区块（`## {主线名} · 主线 · 活跃` + 线头两行 + 完整事件表，非交汇事件数按 storybuilding-specs 数量模板，时序号 T1 起；系统写前校验数量）
- 至少 1 个主角档案（角色类型标注为"主角"）
- 基础世界观框架（至少包含时代背景、核心冲突根源）

初构阶段不生成支线 / 暗线 / 角色线，它们由增量 Skill 按需添加。

未产出的维度直接留空，由后续轮次自然补上，不写「待…」类占位待办。

#### 核心人物与角色线约束

角色类型定义与角色线资格见 storybuilding-specs 人物档案规范（主角/核心人物/Boss/配角）。本阶段硬性约束：

1. 核心人物 ≤ 2 人（不含主角）。宁少勿多——后续增量 Skill 可按需引入。
2. 只有核心人物/Boss 可拥有角色线，每人最多 1 条；配角禁止建线，叙事功能写在事件表「角色」列。

### 步骤 4 — review 审查（每轮收尾必审一次）

**收尾时机**：每轮运行的导航指令显示单元完成/批次完成/配比达标/预算耗尽时收尾。
收尾时调用 review 子代理审查（**本轮产物有任何修改即须审查**——未审直接返回会被系统闸门拦回）。review 调用上限以当轮批次数为准（默认一轮 1 次；用户指示连写 N 条时已放宽至 4N，超出会被拦截）。

**调用时在任务描述中附加**：
"本次为首次骨架构建，请侧重审查结构完整性和可扩展性。骨架阶段不要求内容丰富度，但世界观核心规则的逻辑此轮就要立住。"

**单次审查策略**：无需修改 → 直接返回；建议修订 → 读取 `review/storybuilding.md`，修订对应产物**一次**，**不再二次审查**，直接进入返回步骤。

返回时包含：是否执行修订、是否有质量风险。
格式：`执行修订：否\n质量风险：无`

### 步骤 5 — 回复

用纯文本简要汇报：
- 产出了哪些维度的骨架
- 骨架覆盖范围（故事核心、主线事件表、核心人物）
- 审查状态（未收尾时说明：按配比导航继续增量，尚未 review）
- 下一步建议（未达标 → 继续增量扩展；已收尾 → 说明最终规模）

## 注意事项
- 全部手写产物执行 storybuilding-specs 文风规范（平实叙述）：短句直说、破折号从简、解释过载先简化设定，不写机制说明书式段落
- 只写入系统提示词中定义的文件路径，不修改 demand.md 或其他文件。
- 维度之间保持一致性：引用其他维度的内容时，确保被引用的内容确实存在。
- 线名、事件名全文件唯一且创建后不改（全景/泳道图按名称归属）；不使用 S/E/G 编号。
- **核心人物克制**：≤ 2 人（不含主角），配角禁止建角色线。角色线是稀缺资源，只给真正长期出场且有独立弧光的核心人物。
